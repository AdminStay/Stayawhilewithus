# AI domain

Status: implemented — ops-assistant conversation UI (streaming replies with live tool-call events, real multi-domain tool-use, tool execution history), pending-AI-action approval queue with real execution on approval and its outcome reported back into the conversation, a resolved-actions view, human handoff, `/ai` route.

- **Owned model(s)**: `AiConversation`, `AiMessage`, `AiAction`
- **Permission keys**: `ai_conversations:read`, `ai_conversations:create`, `ai_conversations:update`, `ai_conversations:manage`, `ai_actions:read`, `ai_actions:update`
- **Shape**: `services/ai.service.ts` (`listAiConversations`, `getAiConversation`, `sendAiMessage`, `escalateAiConversation`, `listPendingAiActions`, `listRecentAiActions`, `approveAiAction`, `rejectAiAction`), `schemas/ai.schema.ts`, `components/` (`ConversationList`, `ConversationView`, `ChatComposer`, `PendingActionsList`, `RecentActionsList`), `actions.ts`, `app/api/ai/messages/route.ts` (streaming transport for `ChatComposer`).

**Domain vs. package split**: `packages/ai` (`@stayw/ai`) is the reusable AI platform layer — a modular Orchestrator that coordinates dedicated modules (Conversation Management, Memory Management, Prompt Management, Tool Registry, Tool Execution Engine, Planner, Model Provider, Context Builder, Logging & Telemetry, Evaluation, Human Escalation, Retry & Error Handling), each with its own tests. No permission checks of its own. This domain owns the business-facing feature built on top: the ops-assistant conversation UI, the pending-AI-action approval queue, and human handoff, with its own `assertPermission` calls. Folder name intentionally differs from the permission resource names (`ai_conversations`, `ai_actions`). See `03 Documentation/adr/0007-ai-platform-layer.md` and `packages/ai/README.md`.

**Built fully around the credential boundary, not blocked by it**: `sendAiMessage` always works — it persists the conversation and the user's message either way, and runs the real Orchestrator tool-use loop (see `packages/ai`'s README). If `ANTHROPIC_API_KEY` isn't set (`createModelProvider()` picks `NotConfiguredModelProvider`), a real `SYSTEM`-role message explaining that is persisted and shown in the thread instead of a 500 or a silent failure. Nothing about the conversation UI, history, tool registration, the approval queue, or human handoff depends on Claude actually being configured — and the underlying `ModelProvider` interface isn't Claude-specific either, so swapping providers later wouldn't touch this domain at all.

**Every completed domain has real AI tools now** — 9 domains, 17 tools total. Each domain owns its own `domains/<domain>/ai-tools.ts` (mirrors `properties/ai-tools.ts`, the original) registering:

| Domain         | Read tool (`requiresApproval: false`) | Write tool (`requiresApproval: true`)                                                    |
| -------------- | ------------------------------------- | ---------------------------------------------------------------------------------------- |
| Properties     | `properties.list`                     | `properties.updateStatus`                                                                |
| Guests         | `guests.list`                         | `guests.update`                                                                          |
| Reservations   | `reservations.list`                   | `reservations.updateStatus` (includes cancelling)                                        |
| Tasks          | `tasks.list`                          | `tasks.complete`                                                                         |
| Cleaning       | `cleaning.list`                       | `cleaning.complete`                                                                      |
| Communications | `communications.list`                 | `communications.sendMessage`                                                             |
| Maintenance    | `maintenance.list`                    | `maintenance.resolve`                                                                    |
| Integrations   | `integrations.list`                   | — (read-only; connecting/disconnecting is an infra action, not exposed to the assistant) |
| Audit          | `audit.list`                          | — (append-only log, nothing to write)                                                    |

(`notifications.list` also exists, always scoped to the calling user.) Every write tool follows the same three-line shape: check `ctx.userId`, split the id out of the validated input, call the domain's existing service function (`updateGuest`, `resolveMaintenanceRequest`, ...) — no new business logic, RBAC and mutation shape both stay owned by that domain's service, same as the UI forms. `sendAiMessage` passes every tool name into `runOrchestratorTurn` via `CONVERSATION_TOOL_NAMES` in `ai.service.ts`. Adding a tenth domain's tools: write `domains/<domain>/ai-tools.ts` mirroring an existing one, call its `register*AiTools()` in `ai.service.ts` alongside the others, add the tool name(s) to `CONVERSATION_TOOL_NAMES`.

**Approving an action actually executes it now** — this was a real gap, not a design choice: `approveAiAction` used to only flip `AiAction.status` from `PENDING` to `APPROVED` and stop there; `markActionExecuted`/`markActionFailed` existed in `@stayw/ai` but nothing ever called them, so an approved action just sat there forever. Fixed: after `approveAction()`, `ai.service.ts` calls `executeApprovedTool(action.toolName, action.proposedInput, ctx)` — a small addition to `@stayw/ai`'s Tool Execution Engine (`tools/execution-engine.ts`) that runs a tool's handler directly, the dedicated post-approval counterpart to `executeTool()` (which can't be reused here — calling it again on a `requiresApproval: true` tool would just propose a _second_ action). `ctx` is `{ userId: actor.userId, conversationId: action.conversationId }` — the approving human's identity is what the underlying service's own `assertPermission` checks, same as if they'd clicked the equivalent button in the UI themselves. Success transitions the action to `EXECUTED` (`markActionExecuted`, result saved to `executionResult`) and audits it (`ai_action.executed`); a thrown error (e.g. the approver lacking the underlying permission) transitions to `EXECUTION_FAILED` instead of throwing, audited as `ai_action.execution_failed` with the error message — approving never crashes the request, it just records what happened. The full chain — prompt, the model asking for a tool, the pending-approval pause, approval, `executeApprovedTool` actually running it — is exercised together (real Orchestrator, real Planner, real Tool Registry, real Tool Execution Engine, real Action Approval Framework, only the database mocked) in `packages/ai/src/orchestrator/orchestrator.e2e.test.ts`, plus a website-level test (`ai.service.test.ts`'s "full cycle" describe block) chaining `sendAiMessage` -> `approveAiAction` end to end at this domain's own layer.

**The response step closes the loop, not just the execution step**: `approveAiAction`/`rejectAiAction` now `appendMessage` a `SYSTEM`-role note back into the conversation the action came from — "Approved action executed: tasks.complete.", "Approved action failed: guests.update — <error>", or "Action rejected: <tool> — <reason>". Before this, a human approving something in the pending-actions queue had no way to see the outcome without checking the audit log; the conversation thread just stopped forever at "I've proposed an action that needs approval." The success message carries the same `{ calls: [...] }` `toolCalls` shape the Orchestrator itself writes, so it renders through `ConversationView`'s existing tool-call UI — no new rendering path for this case. `AiAction.conversationId` is optional in the schema; the append is skipped (not guessed) when it's null.

**Resolved actions are visible, not just pending ones**: `PendingActionsList` only ever shows `PENDING` actions — approve or reject one and it simply vanishes from that list. New `listRecentAiActions` (`@stayw/ai`'s `listRecentResolvedActions`, querying `status IN (EXECUTED, EXECUTION_FAILED, REJECTED)` ordered newest-first) + `RecentActionsList` component render the last 20 resolved actions with their real outcome — the execution result for a success, the error for a failure, the reason for a rejection — right on the same `/ai` page.

**Tool execution history is now visible in the thread**: `@stayw/ai`'s orchestrator computed `toolCalls` every turn but never persisted them onto the `ASSISTANT` message row despite `AiMessage.toolCalls` (`Json?`) existing in the schema for exactly this. Fixed with one additive change to `orchestrator.ts` (no loop/control-flow changes): both `appendMessage` calls for the assistant's reply now include `toolCalls: { calls: allToolCalls }` when any tool ran that turn. `ConversationView` renders each message's tool calls underneath it — name, `executed`/`awaiting approval`, and the real output for executed calls.

**Streaming now surfaces tool events too, not just the final text**: `sendAiMessage` returns `toolCalls` alongside `assistantMessage` (it always computed them, just didn't return them before). `app/api/ai/messages/route.ts` emits one `tool_call` SSE event per entry — `{ name, status, output, actionId }` — before streaming the final answer in text chunks, and `ChatComposer` renders each as it arrives (a small badge: tool name + `executed`/`awaiting approval`), then the answer underneath. What's actually streamed is still the **real, already-fully-computed turn** (the route calls the same `sendAiMessage` the old Server Action called — full orchestrator turn, tool-use, approval gate, persistence, all unchanged), sequenced for delivery — not live generation or live tool-call detection. Real interleaved streaming would need `StreamEvent` to carry `tool_use` blocks, which it doesn't yet (`completeStream()` only emits `text_delta`/`message_stop`, see `packages/ai/README.md`), and extending that is a provider-layer change this session deliberately isn't making. The route handler's own comment documents this distinction so it isn't mistaken for real model streaming later.

**Human handoff, both automatic and manual**: hitting the Orchestrator's `maxToolIterations` auto-escalates the conversation (`@stayw/ai`'s `escalateConversation`) and notifies admins. Users can also escalate explicitly via the "Escalate to human" button on an active conversation — both paths write an audit entry (`ai_conversation.escalated`) and notify admins the same way.

**Prompt/tool registration**: `ai.service.ts` calls `registerPrompt(...)` and all 9 domains' `register*AiTools()` functions as module-load side effects (idempotent). There's still no central app-startup hook for this (e.g. `instrumentation.ts`) — worth solving now that this many domains register through one file.

**Not built yet, deliberately deferred**: no context providers are registered (`assembleContext()` returns `[]`), so the `{{context}}` placeholder in the system prompt renders empty for now — Context Engine wiring (pulling in property/reservation/task context per conversation) is a separate, larger feature. OwnerRez and n8n tool integrations are blocked on their own prerequisites (a real OwnerRez credential; n8n's MCP connection being live again) rather than anything in this domain.
