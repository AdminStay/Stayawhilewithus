# Cleaning domain

Status: implemented (list + create + complete + cancel + missed + reschedule + per-job cleaner). See `apps/website/src/domains/properties/` for the reference pattern this follows.

- **Owned model(s)**: `CleaningSchedule`
- **Permission keys**: `cleaning_schedules:read`, `cleaning_schedules:create`, `cleaning_schedules:update`, `cleaning_schedules:delete`, `cleaning_schedules:manage` (delete/manage not yet wired to UI — service functions can be added when needed)
- **Route**: `/cleaning`
- **Lifecycle rules (2026-10-07, enforced in the service, not just the UI — so the `cleaning.complete` AI tool and stale pages get the same answer)**: complete / cancel / missed only from an OPEN job (SCHEDULED or IN_PROGRESS); reschedule an open or MISSED job, never a COMPLETED or CANCELLED one. **Rescheduling a MISSED job reopens it as SCHEDULED** (also on its same date) — `/cleaning` shows a "Reopen" date form on missed rows; the audit entry carries `metadata.reopenedFromMissed`. Every check is part of the UPDATE's `where` (no race), and every transition audits `beforeState` + `afterState` inside the transaction. The plain-form actions treat a `CleaningRuleError` (only possible from a stale page) as "refresh", not an error screen.
- **Rescheduling**: `rescheduleCleaningSchedule` moves `scheduledDate`, records the very first original date in `originalScheduledDate` (subsequent reschedules don't overwrite it — see the field's doc comment on the Prisma model), keeps the backing `Task.dueAt` in sync in the same transaction, and is a no-op (no write, no audit entry) if the new date matches the current one. Surfaced on `/cleaning` (inline per-row form) and on the main dashboard's "Rescheduled Cleanings" section.
- **Cleaner per job (Cleaner Phase 4)**: `CleaningSchedule.cleanerId` is the job's stored cleaner.
  - **Default at creation**: `createCleaningSchedule` copies the property's current, ACTIVE PRIMARY (`findCurrentPrimaryCleanerId`, cleaners domain) in the same transaction. No PRIMARY → `null` ("Needs cleaner"). A TEAM_MEMBER is never chosen automatically, so a team-only property (team, no primary) starts with no cleaner.
  - **Not dynamic (Option A)**: the stored cleaner does not follow later assignment changes — changing a property's PRIMARY on `/cleaners` never modifies existing cleanings; only new ones use the new PRIMARY.
  - **Per-job override**: `assignCleaningScheduleCleaner` sets one job's cleaner — any ACTIVE cleaner, primary or not — or, with `cleanerId: null` (the picker's "Needs cleaner (clear assignment)", submitted as `"none"`), clears it. Clearing picks nobody else and touches only that job. Admin only (`canChangeCleaningCleaner`: `cleaning_schedules:update` AND the global `admin` role — the permission alone isn't enough because the `cleaner` role holds it too). Refused on COMPLETED, CANCELLED and MISSED jobs (`CLEANER_LOCKED_STATUSES`; the status condition is part of the UPDATE). No-op if unchanged (same cleaner, or clearing an unassigned job). Audited as `cleaning_schedule.cleaner_changed` with before/after cleaner id + name (`null`/`null` after a clear), never a phone.
  - **Copy cleaner message (Phase 5.1)**: admin only, on open jobs that have a cleaner. `buildCleanerMessage` (`lib/cleaner-message.ts`) builds the text on the server from exactly five fields — property name, date (UTC), time, cleaning type, cleaner name — never a whole row, so no address, access/lock code, note or phone can be included. The button only writes to the admin's clipboard (with a select-and-copy fallback); it sends nothing, calls no provider/API/server action, and writes no data. Jobs without a cleaner show "Needs cleaner" instead.
  - **Mark cleaner notified (Phase 5.2)**: admin only (same check as above), on open jobs that have a cleaner. `markCleanerNotified` (`services/cleaner-notifications.service.ts`) records that the admin told the cleaner by hand, as an append-only AuditLog entry — action `cleaning_schedule.cleaner_notified`, entity = the job, `afterState` = the cleaner assigned at that moment, actor = the admin, `occurredAt` = when. No migration or extra table (same pattern as lock verification evidence). Refused for a closed job, a job with no cleaner, or if the job's cleaner changed since the page loaded. Each click adds a record (history, not a flag). `/cleaning` shows the latest record per job (`listLatestCleanerNotifications`, admin only, America/Chicago time); a notice sent to a previous cleaner shows as "Not notified yet". Sends nothing and never changes the job or its cleaner. Refused (and not offered) when the job's cleaner is inactive (2026-10-07); Copy cleaner message is likewise not offered.
  - **Jobs needing attention (Phase 5.3)**: an OPEN job (not COMPLETED/CANCELLED/MISSED) with `cleanerId` null — or (2026-10-07) whose stored cleaner is no longer ACTIVE — needs a cleaner (`lib/needs-cleaner.ts`). The dashboard's Needs Attention list shows ONE aggregated row ("N cleaning jobs need attention — These jobs have no cleaner assigned, or their cleaner is inactive.", badge "Needs cleaner") from `listCleaningJobsNeedingCleaner`, linking to `/cleaning?view=needs-cleaner`; `/cleaning` shows a matching notice and that view lists only those jobs (each already marked "Needs cleaner"). Requires `cleaning_schedules:read` AND `cleaners:read` — without the latter a job's cleaner is hidden, so nothing is shown and the filter is ignored. Read-only: assigns nothing, sends nothing; no new permission, table or migration.
  - **Create form**: submits `cleanerId` explicitly, pre-filled with the PRIMARY; a value other than the default (another cleaner, or "" = none) needs admin.
  - **Visibility**: the job's cleaner (id/name/status only) is returned and shown only with `cleaners:read` (same gate as the Cleaner column on `/properties`); without it `cleaner` is null, including for the `cleaning.list` AI tool.
  - **Not in this phase**: creating cleanings from reservations/checkouts, moving open jobs on a PRIMARY change, cleaner notifications.
- **Not yet implemented**: no `triggerWorkflow` call yet — no n8n workflow exists for `cleaning_schedule.created`/`.completed` (n8n instance confirmed empty 2026-08-06; n8n MCP connection itself is not currently available this session — see `HANDOFF.md`).

Cleaning-specific detail (scheduled times, cleaning type) on top of the shared `Task` assignment record — see `03 Documentation/architecture/erd.md` for the Task/CleaningSchedule/MaintenanceRequest relationship. `createCleaningSchedule` creates the backing `Task` (type `CLEANING`) and the `CleaningSchedule` row together in a single `prisma.$transaction`, since `CleaningSchedule.taskId` is a required unique FK. `completeCleaningSchedule` likewise updates both rows (`CleaningSchedule.status → COMPLETED`, `Task.status → DONE`) in one transaction.
