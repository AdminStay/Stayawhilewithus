# Users domain

Owns `UserRole` assignment and in-app team lifecycle (invite, deactivate). Does not own `User` profile fields (Clerk + `platform/identity/` own that) or `Role`/`Permission` definitions (those are seeded, not editable from this UI).

- **Services**: `services/users.service.ts` — `listUsersWithRoles`, `listAssignableRoles`, `assignUserRole`, `revokeUserRole`, `inviteTeamMember`, `listPendingInvitations`, `revokeInvitation`, `deactivateTeamMember`.
- **Schemas**: `schemas/users.schema.ts` — `assignUserRoleSchema`, `inviteTeamMemberSchema`.
- **Components**: `components/UserList.tsx`, `components/InviteTeamMemberForm.tsx`, `components/PendingInvitationsList.tsx`, `components/RolePermissionsList.tsx`.
- **Actions**: `actions.ts` — `assignUserRoleAction`, `revokeUserRoleAction`, `inviteTeamMemberAction`, `revokeInvitationAction`, `deactivateTeamMemberAction` (Server Actions).
- **Permissions**: `users:read` (view users + pending invitations), `roles:read` (view the assignable-role list), `roles:manage` (assign/revoke a role), `users:create` (invite), `users:delete` (revoke an invitation, deactivate a team member). All five already existed in the permission catalog (`packages/auth/src/permissions.ts` / `packages/database/prisma/seed.ts`) — **nothing was added there**, and no new role was created. As seeded, only the `admin` role (`permissionKeys: "*"`) holds any of them, so this whole domain is admin-only by construction, enforced server-side via `assertPermission` as the first line of every service function — the `/users` nav link itself is not hidden from other roles, matching every other route in this app (the page throws `ForbiddenError`, caught by `app/(dashboard)/error.tsx`).
- **Route**: `/users` (`apps/website/app/(dashboard)/users/page.tsx`).

## Why this domain exists

Clerk sign-in only authenticates and JIT-provisions a `User` row with zero `UserRole` assignments (`platform/auth/get-current-user.ts`) — every domain service's `assertPermission` then fails for a brand-new real sign-in until an admin grants a role. Before this domain, the only way to do that was `packages/database/scripts/grant-role.ts`, a CLI script run directly against the database. That script is **still valid and unchanged** — keep it as an emergency/manual fallback for when the app itself is unreachable — but day-to-day role granting should go through this UI now.

## Behavior notes

- **Role assignment is idempotent**: assigning a role a user already holds (same user + role + property scope) is a no-op, not an error — mirrors `grant-role.ts`'s existing behavior.
- **Global vs. property-scoped**: `UserRole.propertyId` is nullable (`null` = global). The assign form defaults to "Global"; picking a property scopes the grant to it, same model `packages/auth/src/rbac.ts` already reads.
- **Last-global-admin protection**: both `revokeUserRole` and `deactivateTeamMember` refuse to remove the last remaining global `admin` assignment in the system (`ConflictError`) — role management, and the account holding it, can't accidentally lock the app out of itself through the UI. `grant-role.ts` remains available as a direct-database escape hatch regardless.
- **Inviting never creates a fake user**: `inviteTeamMember` only sends a real Clerk invitation (`platform/identity/invite-clerk-user.ts`) — no local `User` row, no password, no bypass of Clerk auth. The invitee's row is created the normal way — JIT provisioning or the Clerk webhook — only once they actually accept and sign in. Inviting an email that already has a `User` row (case-insensitively) is rejected with `ConflictError` rather than sending a duplicate invite.
- **Optional role selection at invite time**: `inviteTeamMember` accepts an optional `roleId`/`propertyId`, validated the same way `assignUserRole` validates them. If given, they're carried as the Clerk invitation's own `publicMetadata` (`pendingRoleId`/`pendingPropertyId`/`pendingRoleInvitedByUserId` — the last so the resulting `UserRole`/audit entry is attributed to the inviting admin, not left blank). Clerk carries an invitation's `publicMetadata` onto the resulting user on signup; both creation paths (`sync-clerk-user.ts`'s webhook and `get-current-user.ts`'s JIT fallback) call the shared `applyPendingRoleFromInvitation` at the exact moment a **brand-new** `User` row is created — never on an update or on claiming a pre-existing row by email — so a role chosen once at invite time is applied exactly once. If the role or property was deleted between invite and acceptance, this skips silently rather than failing account creation; the person just ends up with no role, same as inviting without one. Omitting `roleId` preserves the original flow exactly: invite now, assign a role later from this page's per-user "Assign a role" control.
- **Deactivating revokes access without deleting anything**: `deactivateTeamMember` sets `User.status = "DEACTIVATED"` only — never `deletedAt`, never touches their `UserRole` rows or any `AuditLog` row that references them. The row stays visible in this list with a "Deactivated" badge instead of disappearing. Access is actually blocked at the authentication boundary: `getCurrentUser()` now throws `AccountDeactivatedError` for any non-`ACTIVE` (or soft-deleted) row on every single request, before any `assertPermission` call runs — so this is enforced uniformly across every route and Server Action in the app, not just this domain's own checks. There's deliberately no "reactivate" action yet (not asked for); the data is left in a state where one would be trivial to add.
- **Email matching is case-insensitive everywhere identity is resolved**: `getCurrentUser()`, the Clerk webhook sync (`platform/identity/sync-clerk-user.ts`), and `inviteTeamMember`'s duplicate check all normalize to lowercase before comparing/storing, so `Admin@StayAWhileWithUs.com` and `admin@stayawhilewithus.com` can never become two different application users. `User.email`'s database-level unique constraint is case-sensitive on its own — this normalization at every write site is what actually makes it behave as a case-insensitive key.
- **Roles & permissions reference table**: `RolePermissionsList.tsx` shows each role's actual granted permission keys (grouped by resource), sourced from `listAssignableRoles`'s `rolePermissions.permission.key` include — read-only, no new write path, no schema change. The `admin` role renders as "Unrestricted — all permissions" instead of enumerating all ~75 keys, since that's the more honest and readable statement of what `permissionKeys: "*"` actually means.
