# Cleaners domain

Status: Phase 3 implemented (cleaners + property assignments + history). Dashboard-managed data — no roster is hard-coded anywhere; every cleaner and assignment is created and changed from `/cleaners`.

- **Owned models**: `Cleaner` (a contact record, not a login account; its own primary phone), `CleanerContact` (zero or more backup numbers per cleaner, each with an optional contact name/relationship — empty means another number for the cleaner themself), `PropertyCleanerAssignment`. `CleaningSchedule.cleanerId` is set by the cleaning domain (Phase 4 — see `../cleaning/README.md`): a new cleaning copies the property's current ACTIVE PRIMARY via `findCurrentPrimaryCleanerId`; pickers use `listCurrentPropertyCleanerOptions` / `listActiveCleanerOptions` (ids + names only, no phones).
- **Permission keys**: `cleaners:read` (view; phones masked), `cleaners:manage` (every write, and the only key that receives full phone numbers). Admin only for now (wildcard / `scripts/grant-cleaners-permissions.ts`); excluded from `read_only`'s blanket grant. Which other roles get read/manage is a pending Kenny/Michelle decision.
- **Routes**: `/cleaners` (cleaners + property assignments); `/properties` shows a "Cleaner" column (names only) to anyone with `cleaners:read`.
- **Assignment rules**: a row is current while `endedAt` is null; changes end the current row and start a new one (history is never edited). The database enforces one current PRIMARY per property and one current row per cleaner per property (partial unique indexes in `20261003120000_add_cleaners`). A property may have TEAM_MEMBERs and no PRIMARY — e.g. a team whose primary contact isn't decided yet; "Make primary" promotes a team member. Only ACTIVE/ONBOARDING, non-deleted properties and ACTIVE cleaners can be assigned. A property that later goes Inactive/Offboarded/removed while it still has cleaners stays listed on `/cleaners` (after the operational ones, marked, Remove-only) so those cleaners can be removed and then deactivated.
- **Deactivation**: cleaners are never deleted. Deactivation is refused while a cleaner holds any current assignment, or (2026-10-07) is the stored cleaner on any OPEN cleaning (SCHEDULED/IN_PROGRESS) — reassign or clear those on `/cleaning` first.
- **Phones** (primary and backup): stored E.164 (`lib/phone.ts`); masked on the server (`toCleanerView`) for anyone without `cleaners:manage`; audit entries store the last 4 digits only. A backup number can't repeat the cleaner's primary number, or another backup of the same cleaner (DB unique).
- **Assignment changes never touch cleanings (Phase 4, Option A)**: changing/ending/adding an assignment leaves every existing cleaning's stored cleaner as-is; an admin changes individual jobs on `/cleaning`.
- **Not in this phase**: moving open future cleanings on a change, any notification or SMS (Phase 5 — Google Voice is a separate decision; nothing here depends on it).
